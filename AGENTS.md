# Правила проекта

## Автоматически генерируемые файлы

Файлы, которые генерирует `updateui.sh`, не изменять: никаких правок и никаких
добавленных комментариев или docstring, в том числе через отдельные скрипты
постобработки. Их содержимое создают только штатные генераторы интерфейса и ресурсов.
Правила документирования классов и методов применяются к коду, написанному вручную,
и не применяются к автоматически генерируемым файлам:

- `ElParts.py`
- `ElAppPathWnd.py`
- `ElLogWnd.py`
- `ElHdrEditWnd.py`
- `ElPluginsWnd.py`
- `ElUnitsWnd.py`
- `resources.py` (промежуточный файл `resources.pyx` также не редактировать вручную).

Изменения интерфейса и ресурсов вносить в исходные файлы `.ui`, `.qrc` и ресурсы, затем запускать `updateui.sh` для перегенерации. Поведение приложения изменять в файлах, написанных вручную. Это правило распространяется и на новые файлы, которые в дальнейшем будет генерировать `updateui.sh`.

## Тексты окон и языки

Во всех элементах интерфейса скрывать внутренние ID записей БД, если пользователь
явно не потребовал их отображения. В моделях сохранять ID для связей и операций
с данными.

Подписи элементов интерфейса для двух языков задавать в отдельном модуле `ElWindowTexts.py`, отдельной функцией для каждого окна. Вызывать её из кода окна при инициализации после создания виджетов и при смене языка. Не вносить изменения для локализации в автоматически генерируемые Python-файлы. Каталоги переводов и управление языком находятся в `translations/` и `ElTranslations.py`.


## Документация / Documentation

Всю документацию проекта вести на русском и английском языках. При создании
документа сразу добавлять обе версии; при изменении существующего документа
синхронно обновлять обе версии. Если перевода ещё нет, создавать его.
Сохранять принятую пару имён файлов; для новых документов в `docs/` использовать
`<name>.md` для русского текста и `<name>.en.md` для английского.
В каждой версии добавлять ссылку на другую. Ссылки из `README.md` вести на
английскую документацию, из `README.ru.md` — на русскую.

Maintain all project documentation in Russian and English. Create both versions
for every new document and update both together when editing an existing document.
If a translation is missing, create it. Preserve established filename pairs;
for new documents in `docs/`, use `<name>.md` for Russian and `<name>.en.md`
for English. Link each version to its counterpart. Link `README.md` to English
documentation and `README.ru.md` to Russian documentation.

## Тестовые базы и резервные копии

После успешного полного прогона тестов удалять временную `test_db.sqlite` в корне
проекта вместе с её SQLite sidecar-файлами и тестовые резервные копии
`*.sqlite.bak*`, `*.sqlite3.bak*`, `*.db.bak*` непосредственно в `tests/`.
При неудаче сохранять временную БД и три последних бэкапа каждой тестовой базы.
Использовать `tools/cleanup_test_databases.py --success` или `--failed`;
`build.sh -t` вызывает нужный режим автоматически. Исходную `tests/imported.sqlite`,
входные данные `tests/input/` и архивные фикстуры не удалять.


## Архитектура кода и работа с БД

1. Запросы приложения, структура таблиц и миграции находятся в
   `ElData/ElDBScheme.py`. Соединение, выполнение SQL, транзакции, PRAGMA,
   системные метаданные и остальные специфичные для SQLite операции находятся
   в `ElData/ElDBConnect.py`. Вне этих двух файлов SQL не выполняется.
   Исключение — тесты: в них разрешены прямые SQL-запросы.
2. Классы и структуры данных, полученных из БД, размещаются в отдельных файлах.
   Перед созданием нового файла для этой цели нужно спросить у пользователя его
   название. Для существующих областей согласованы имена: проекты —
   `ElDBDataProj.py`, каталог — `ElDBDataParts.py`, плагины — `ElDBDataPlagins.py`,
   справочники единиц и базовых типов — `ElDBDataUnits.py`.
   Классы внешних API, например публичные модели плагинов, из этого правила исключены.
3. Манипуляции данными БД выполняются через классы данных либо как минимум через
   соответствующие файлы данных (`ElDBDataParts.py`, `ElDBDataProj.py` и далее
   по той же схеме). Эти слои делегируют обращения и SQL в `ElData/ElDBScheme.py`.
4. Все константы собираются в `ElConstants.py`. Исключение — константы,
   описывающие структуру БД, SQL-запросы и их части: они остаются в
   `ElData/ElDBScheme.py`, а SQLite-инфраструктура — в `ElData/ElDBConnect.py`.
5. У каждого класса должен быть комментарий-описание: назначение, основное
   применение и хранимые данные.
6. У каждого метода класса должен быть краткий комментарий-описание: действие,
   параметры, ожидаемые типы и, если заданы ограничения, допустимые значения. 
   Параметры и переменные описываются в YARD (Ruby) формате. 

Порядок применения:
- Правило 1 выполняется для текущего кода сейчас.
- Требования к описаниям классов и методов (пункты 5 и 6, включая формат YARD)
  применяются ко всему коду, который агент создаёт или изучает в процессе генерации
  и изменения кода. При изучении существующего кода недостающие или неполные
  описания дополняются без отдельной команды пользователя.
- Файлы, создаваемые `updateui.sh`, полностью исключены из требований к описаниям:
  в них не добавляются правки, комментарии или docstring ни вручную, ни скриптами.
- Правила 2–4 применяются к новым частям кода; существующие части переносятся или
  перерабатываются только по отдельной команде. По правилам 2 и 3 код и данные
  иконок пока не переносить.
- Написание исправлять.


## Диагностические логи

При добавлении и изменении операций добавлять полезные DEBUG-логи через
`ElCommon.setLogger(__name__)`: начало и завершение, ключевые параметры,
результат, причины пропуска или отмены. Для исключений сохранять traceback.
Логи должны попадать в настроенные консоль и файл; не засорять их сообщениями
из каждой перерисовки ячейки. Внутренние ID допустимы в диагностических логах.
