# Установка и запуск импортёров

Состояние: 19 ноября 2026 года. API 1, протокол 1, схема БД 6.

## Работа в приложении

1. Собрать плагин из `ElPartsPluginSrc/kicad`: `./build.sh -p`.
2. Открыть **Настройки → Плагины… → Установить из файла…** и выбрать
   `dist/plugins/partsdb_kicad-0.1.0-py3-none-any.whl`.
3. Проверить показанные название, описание, автора, систему и версию пакета.
   Установка той же версии или нового wheel с тем же ID обновляет плагин.
   Для другого ID той же системы можно выбрать замену существующего импортёра
   или установку рядом с ним.
4. На вкладке **Проекты** нажать **Добавить проект**, выбрать импортёр (если
   доступно несколько) и файл или URI источника. KiCad поддерживает локальные
   `.kicad_pro` и `.kicad_sch`; поддержку других URI определяет конкретный плагин.
5. Проверить предпросмотр позиций и предупреждения, затем нажать **Сохранить**.
   До этого момента результат существует в памяти; отмена не записывает проект.
6. Кнопка **Обновить данные** выполняет повторный импорт с предпросмотром
   добавленных, изменённых и удалённых позиций.

В списке проектов показывается система установленного плагина. Отключённый
плагин нельзя выбрать для нового импорта или запустить при перезагрузке.
Удаление плагина оставляет проекты, компоненты и сопоставления в БД.
Для продолжения импорта после удаления можно снова установить плагин с тем же ID.

Настройки плагина недоступны, если API не объявляет их схему. У KiCad-импортёра
сейчас нет пользовательских настроек; кнопка выключена с пояснением.
Кнопка **Журнал** показывает записи текущего окружения плагина.

## Сопоставления со складом

Во вкладке проекта видны импортированные позиции, выбранные складские карточки
и отметки необходимости перепроверки. Панель **Несопоставленные детали**
показывает позиции без подтверждённого соответствия. Это не означает,
что подходящей детали нет на складе.

Для ручного сопоставления выбрать деталь в складском каталоге, затем открыть
контекстное меню строки компонента проекта и выбрать **Сопоставить с выбранной
деталью склада**. После подтверждения сохраняется связь с `PARTS.id`.
Пункт **Удалить сопоставление со складом** удаляет только выбранную связь.
Автоматический подбор замен и оценка достаточности запасов в эту реализацию
не входят. Импорт не создаёт складские карточки и не изменяет остатки.

## Тип и проверка плагина

Функциональный тип объявляется самим плагином в `plugin_type` манифеста и методе
`get_plugin_type()`. Допустимы глобальные значения `project_import`, `parts_order`,
`shipment_tracking` — импорт, заказ деталей и отслеживание посылок.
Их константы находятся в `ElPartsPluginApi/constants.py`.

При установке неизвестный тип или несовпадение метода с манифестом приводят
к отказу без регистрации плагина. Для импорта проекта выбираются только включённые
плагины `project_import`; тип проверяется ещё раз перед выполнением.
Замена и обновление требуют того же типа и той же внешней системы.
Тип отображается в списке и в поле «Тип» окна менеджера; рядом указывается система.
Для заказа и отслеживания пока определён общий контракт типа, без рабочих операций.

## Хранение и окружения

Без отдельной настройки каталог плагинов расположен рядом с конфигурацией
PartsDB. Для стандартной `~/.elworks/elworks.conf` это:

```text
~/.elworks/plugins/
├── plugins.json
└── .installs/
    └── org.partsdb.kicad-<случайный суффикс>/
        ├── venv/
        ├── runtime/
        │   ├── worker.py
        │   ├── ElPartsPluginApi/
        │   └── ElPluginMgr/
        └── plugin.log
```

В SQLite создана таблица `PLUGINS`: ID, `plugin_type`, название, версия, API,
внешняя система, описание, автор, признак включения и полный JSON-манифест.
Схема 5 → 6 добавляет таблицу атомарно, сохраняя проекты и позиции.
Установка, замена, включение и удаление обновляют метаданные текущей БД;
`PluginManager.sync()` синхронизирует её при открытии окна или смене БД.
Файловый реестр хранит сведения об установленных окружениях и их путях.
Если пакет менялся при закрытой БД, при синхронизации её проекты отмечаются
для повторного импорта. `PROJECTS.plugin_id` сохраняется и после удаления
плагина — внешнего ключа на `PLUGINS` у него нет.

Старые wheel без `plugin_type` нужно пересобрать с новым методом API.
Старые записи файлового реестра, поддерживавшие только импорт, распознаются
как `project_import`, но запуск всё равно требует подтверждения типа worker.

В разделе конфигурации `plugins` можно задать `directory` и путь `python`.
Например, для явно выбранного Python:

```yaml
plugins:
  directory: ~/.elworks/plugins
  python: /absolute/path/to/python3
```

Путь интерпретатора в примере нужно заменить существующим; без этих настроек
используются значения по умолчанию.
В исходном запуске по умолчанию используется Python приложения. Самостоятельная
сборка PyInstaller создаёт окружения с помощью установленного `python3` из PATH
либо явно указанного интерпретатора. Требуется Python 3.9 или новее.
Исходники SDK и worker включаются в сборку приложения как ресурсы для копирования
в отдельное окружение.

Установщик читает манифест до выполнения кода, проверяет API, ID и точку входа,
создаёт новое окружение и устанавливает wheel через pip без сетевых обращений.
Дополнительные зависимости должны быть доступны в виде wheel рядом с выбранным
пакетом. Для первого KiCad-импортёра внешних зависимостей нет. API предоставляет
PartsDB, копируя SDK в runtime; сам плагин не должен требовать отдельный
дистрибутив SDK через pip в этой версии механизма установки.

Затем отдельный процесс проверяет создание плагина, совпадение его типа с манифестом
и, для импортёров, поддерживаемые форматы.
Только успешный кандидат записывается в реестр; при ошибке старый плагин остаётся
доступен. Переключение связанных проектов и отметка `needs_reload=1` выполняются
для текущей открытой БД, затем удаляется прежнее окружение. Приложение не обходит
другие базы пользователя. Неиспользуемое окружение может остаться на диске при
ошибке его удаления; действующим считается только поколение, указанное в реестре.

## Процесс и протокол

`PluginRunner` запускает Python окружения с `-I -X utf8` и скопированным `worker.py`.
Код плагина не импортируется в процесс Qt. В stdin передаётся один JSON-запрос:
`protocol_version`, `action`, `manifest`, `source_uri`, `expected_type`.
Для `import` ожидается `project_import`; для `inspect` — тип манифеста.

Ответы — JSON-строки с `protocol_version=1` и типами:

- `progress`: `completed`, `total`, `message`;
- `log`: `level`, `message`;
- `result`: `plugin_type` и `result` — проект либо перечень форматов при `inspect`;
  для двух других типов `inspect` возвращает пустой список, без вызова операций импорта;
- `error`: `error_type`, `message`.

Каждый плагин реализует `get_plugin_type()`. Worker проверяет ответ
до выполнения операции и указывает тип в результате; runner проверяет его повторно.
Плагин получает `self.context` с методами `log`, `progress`, `check_cancelled`.
Метод импорта по-прежнему принимает только `source_uri`.
Обычные `print()` плагина перенаправляются в stderr и не повреждают протокол.
Журнал сохраняет сообщения и диагностику, ограничивает размер и выполняет ротацию.

По умолчанию запуск ограничен 120 секундами. При отмене или тайм-ауте процесс
завершается; результат не записывается. Чтение stdout/stderr выполняется параллельно,
а размер одного сообщения ограничен 16 MiB. Отдельный процесс изолирует сбои
от Qt, но не является песочницей для недоверенного Python-кода.

Работа выполняется через `QThread`; запись SQLite происходит после завершения
фоновой задачи в GUI-потоке. Данные проходят проверку полей, флагов, JSON,
конечности нормализованных значений и уникальности ID и обозначений.

## Запись и повторный импорт

`ProjectRepository` проверяет и преобразует данные, затем вызывает методы
`DBScheme` из `ElData/ElDBScheme.py`. Запросы приложения находятся в этом файле,
а соединение, транзакции и системные операции SQLite — в `ElData/ElDBConnect.py`. `DBScheme.saveImportedProject()` включает внешние ключи
и выполняет изменения проекта одной транзакцией, без промежуточного `commit()`.
Существующие позиции обновляются по `(project_id, external_id)`, их внутренние ID
сохраняются. Выбранные сопоставления не теряются при переименовании обозначений.
Изменения типа, номинала, модели, символа, корпуса, описания, флагов или
пользовательских требований отмечают связь `needs_review=1`.

Исчезнувшие позиции удаляются вместе со своими сопоставлениями. Остатки склада
сохраняются. `last_imported_at` и `needs_reload=0` записываются только в успешной
транзакции. Ошибка на любом шаге сохраняет прежний результат и дату импорта.
Отдельной истории попыток и новых таблиц для этого не создаётся.

## Проверка и очистка тестовых БД

Все команды выполняются из корня PartsDB с Python виртуального окружения:

```sh
./build.sh -t        # все тесты, затем очистка или ротация
./build.sh -tp       # все тесты, очистка, затем wheel плагина
./build.sh -tpb      # все тесты, очистка, приложение и wheel
```

`-p` собирает только плагин, `-b` — только приложение; без `-t` тесты
и очистка не запускаются. `-a` выполняет генерацию UI, тесты с очисткой и сборку
приложения; для wheel добавляется `-p`.

Для отдельных тестов плагина:

```sh
python -m unittest discover -s tests/kikad_plugin -v
```

Без `kicad-cli` пропускается только сверка с новым экспортом KiCad.
Для её запуска можно задать `KICAD_CLI`; сохранённый эталон и остальные тесты
не требуют установленного KiCad. Сборка wheel внутри теста требует pip
и setuptools с поддержкой `bdist_wheel`.

После успешного полного прогона `build.sh` вызывает
`tools/cleanup_test_databases.py --success`: удаляются `test_db.sqlite` в корне,
её `-wal`, `-shm`, `-journal` и тестовые бэкапы непосредственно в `tests/`.
В корне также очищаются бэкапы только `test_db.sqlite`.
Поддерживаются имена `<база>.sqlite.bak`, `.sqlite3.bak`, `.db.bak` и их
суффиксы через `-` или `.`. SQLite sidecar-файлы бэкапа удаляются вместе с ним.

При ошибке вызывается `--failed`: временная БД сохраняется, для каждой базы
остаются три последних бэкапа по времени изменения. Код ошибки тестов сохраняется,
сборка не начинается. Исходная `tests/imported.sqlite`, `tests/test_db.sqlite`,
все входные данные `tests/input/`, архивные фикстуры и рабочие базы вне этой
области очисткой не затрагиваются.

После прямого полного запуска unittest очистка выполняется явно:

```sh
python tools/cleanup_test_databases.py --success  # только после успеха всех тестов
python tools/cleanup_test_databases.py --failed   # после ошибки
```

Число сохраняемых при ошибке копий можно задать через `--keep-backups N`.
Правило закреплено в `AGENTS.md`; проверки очистки — в
`tests/test_cleanup_test_databases.py`.

Тесты используют временные базы и окружения. Проверяются установка настоящего
wheel и импорт 49 позиций, обновление и замена, ошибка записи реестра, отключение
и удаление, протокол, аварийное завершение, тайм-аут, отмена, предпросмотр,
сохранение и повторный импорт, сохранение и перепроверка сопоставлений, откат
при ошибке SQLite и интерфейс на двух языках.

См. также [пример данных и раскладку по таблицам](kicad-import-output-and-database-mapping.md).


Последняя полная проверка 19 ноября 2026 года: **340 тестов прошли**, включая
сверку с установленным KiCad, три типа плагинов, отказ при несовпадении типа,
миграцию 5 → 6 и запись `PLUGINS`. Автоматическая очистка тестовых БД выполнена.
Приложение и wheel собраны. Проверки схемы выполнялись на временных базах;
личная база склада в рамках этой доработки не мигрировалась.


Проверка `tests/test_database_access_boundary.py` контролирует разделение запросов
приложения (`ElData/ElDBScheme.py`) и драйвера (`ElData/ElDBConnect.py`), а также
сохранение незавершённых транзакций. Методы драйвера проверяются в
`tests/test_db_connect.py`; их описание — [SQLite-драйвер](sqlite-driver.md). Сами тесты могут обращаться к SQLite напрямую.
