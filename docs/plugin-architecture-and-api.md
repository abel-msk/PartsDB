# Плагины PartsDB: архитектура и API

Актуальность: 21 ноября 2026 года. Описана текущая реализация: API 1,
протокол 1. Конкретный импортёр KiCad описан отдельным документом.

Порядок установки и работы: [Установка и запуск импортёров](plugin-runtime.md).
Структура хранения: [единый справочник таблиц и справочников](database-schema.md).
История изменения хранения: [все миграции](database-migrations.md).
Фактический результат импорта: [импортёр KiCad и пример результата API](kicad-importer.md).

## Назначение и границы ответственности

Плагин читает внешний проект и возвращает стандартные Python-модели.
PartsDB устанавливает плагин, запускает его в отдельном процессе, показывает
предпросмотр и сохраняет подтверждённый результат. Публичный API не зависит
от Qt, SQLite и внутренних классов склада.

Один проект связан с одним текущим импортёром; связь обслуживает приложение.
В импорт передаётся только `source_uri`; название проекта, описание,
внешние ID, свойства и компоненты возвращает плагин. Сведения о внешней
системе предоставляет манифест. Несколько плагинов могут поддерживать одну систему.

Импорт не создаёт складские карточки и не изменяет остатки. Сопоставление
позиции с существующей деталью склада подтверждается отдельно.

## Типы плагинов

Тип определяет сам плагин: поле `plugin_type` в манифесте и обязательный метод
`Plugin.get_plugin_type()` должны возвращать одно значение. Глобальные константы
объявлены в `ElPartsPluginApi/constants.py`, экспортируются из SDK и доступны
в `constants.py` приложения:

| Константа | Значение | Назначение |
|---|---|---|
| `PLUGIN_TYPE_IMPORT` | `project_import` | Импорт проекта |
| `PLUGIN_TYPE_PARTS_ORDER` | `parts_order` | Заказ деталей |
| `PLUGIN_TYPE_SHIPMENT_TRACKING` | `shipment_tracking` | Отслеживание посылок |

`PLUGIN_TYPES` содержит все три допустимых значения. Для заказа и отслеживания
реализованы объявление типа, проверка и регистрация. Выполнение заказа и получение
статуса посылки остаются отдельными будущими API.

Неизвестный тип отвергается при чтении wheel. После установки во временное
окружение worker вызывает `get_plugin_type()` и сравнивает ответ с манифестом.
При несовпадении установка не регистрируется, прежний плагин сохраняется.
Перед импортом проекта runner дополнительно требует `PLUGIN_TYPE_IMPORT`,
а worker повторяет проверку до вызова `import_project()`.

Тип входит в манифест и проверяется приложением при установке и запуске. `system_id` описывает внешнюю систему, а не функциональный тип.

## Манифест

В wheel должен находиться ровно один файл `partsdb-plugin.json`:

```json
{
  "id": "org.partsdb.kicad",
  "name": "KiCad Importer",
  "version": "0.1.0",
  "api_version": 1,
  "plugin_type": "project_import",
  "description": "Import components from KiCad schematic projects",
  "author": "PartsDB",
  "system_id": "kicad",
  "system_name": "KiCad",
  "capabilities": ["project_import"],
  "entry_point": "partsdb_kicad.plugin:KiCadImporter"
}
```

Все показанные поля обязательны. `PluginManifest.from_dict()` отвергает
неизвестные поля, неподдерживаемую версию API, некорректные идентификаторы
и точку входа. `plugin_type` должен входить в `PLUGIN_TYPES`; `capabilities`
в текущей версии содержит одно совпадающее значение, например `["project_import"]`.
`version` — версия пакета, `api_version` — версия контракта с приложением.

`id` — постоянный идентификатор плагина для связи с проектами. `system_id` применяется при замене
другим плагином, `system_name` показывается в интерфейсе. Систему не определяют
по имени Python-пакета или расширению файла.

Установщик читает манифест до выполнения кода. Затем worker импортирует класс
из `entry_point`, проверяет наследование от общего `Plugin`, создаёт экземпляр
без аргументов и проверяет его тип. Импортёр дополнительно должен наследовать
`ProjectImporter` и объявлять поддерживаемые форматы.

## Интерфейс импортёра

```python
from ElPartsPluginApi import PLUGIN_TYPE_IMPORT
from ElPartsPluginApi.importers import (
    ProjectImporter, ImportFormat, ProbeResult, ImportedProject,
)

class ExampleImporter(ProjectImporter):
    def get_plugin_type(self) -> str:
        return PLUGIN_TYPE_IMPORT

    def get_import_formats(self) -> list[ImportFormat]:
        return [ImportFormat('example', 'Example project', ['.example'])]

    def probe(self, source_uri: str) -> ProbeResult:
        ...

    def import_project(self, source_uri: str) -> ImportedProject:
        ...
```

Пример показывает сигнатуры; тела `probe` и `import_project` реализует автор.

| Метод | Результат |
|---|---|
| `get_plugin_type()` | Один из трёх глобальных типов; обязан совпадать с манифестом |
| `get_import_formats()` | Список `ImportFormat(id, name, extensions)` |
| `probe(source_uri)` | `ProbeResult(supported, reason=None)` |
| `import_project(source_uri)` | `ImportedProject` |
| `get_components(source_uri)` | Список `ImportedComponent`; базовая реализация возвращает `import_project(source_uri).components` |

Поддержку URI определяет конкретный импортёр. KiCad принимает локальные пути
и `file:` URI для `.kicad_pro` и `.kicad_sch`. HTTP/HTTPS и старые `.sch`
этим плагином пока не поддерживаются. `probe` проверяет корневой источник;
полный обход иерархии выполняется при импорте.

### Контекст

Перед вызовом метода worker присваивает экземпляру `self.context`:

```python
self.context.log('info', 'Reading project')
self.context.progress(completed, total=None, message='')
self.context.check_cancelled()
```

Контекст не меняет сигнатуру `import_project(source_uri)`. Он передаёт журнал
и прогресс. `ImportContext` также допускает callback отмены при самостоятельном
использовании SDK; текущий runner отменяет выполнение завершением процесса.
Декларативная схема пользовательских настроек в API 1 не реализована.

## Возвращаемые модели

`ImportedProject` содержит `name`, `description`, `external_id`, `properties`,
`components` и `warnings`. `ImportedComponent` описывает одну физическую позицию:
ID, обозначение, категорию, исходное значение, нормализованный номинал, модель,
символ, посадочное место, описание, флаги и исходные свойства.

Полные определения: [models.py](../ElPartsPluginApi/importers/models.py).
Хранение и преобразование моделей: [справочник таблиц](database-schema.md#пример-преобразования-результата-api-в-строки-бд).
Пример возвращаемого результата: [импортёр KiCad](kicad-importer.md).

`Nominal(value, unit)` хранит число десятичной строкой, например
`Nominal(value='4700', unit='ohm')`. Исходное `4k7` остаётся в `value_raw`.
Если номинал не распознан, `nominal` равен `None`.

Одна запись — одна физическая позиция. Количество одинаковых деталей вычисляет
приложение группировкой. Многосекционные символы объединяет импортёр; повторные
экземпляры листов должны иметь разные внешние ID. Отдельных полей листа и количества нет.
Служебные символы питания исключаются; DNP и исключённые из BOM позиции сохраняют флаги.

Категория `kind` — непустая строка, а не закрытый enum. KiCad использует категории
`resistor`, `capacitor`, `inductor`, `diode`, `led`, `transistor`, `ic`, `module`,
`connector`, `relay`, `switch`, `fuse`, `crystal`, `test_point`, `mounting_hole`,
`other`, `unknown`. Это результат классификации исходника, без проверки даташита.

`ImportWarning(code, message, component_id=None, source_file=None)` позволяет
вернуть диагностическое сообщение вместе с проектом. Предупреждения показываются
в предпросмотре. Хранение служебных данных — ответственность приложения;
структура описана в [справочнике таблиц](database-schema.md).

### Проверка результата и ошибки

Сериализация через `protocol.py` проверяет поля моделей, непустые обязательные
строки, уникальность ID и обозначений, логические флаги, структуру коллекций,
конечность нормализованного числа и возможность представить свойства как JSON.
Проверки выполняются в worker и на стороне приложения; repository проверяет
результат ещё раз перед началом записи.

| Исключение | Смысл |
|---|---|
| `UnsupportedFormatError` | Неподдерживаемый формат или URI |
| `InvalidSourceError` | Повреждённый или неоднозначный источник |
| `MissingSourceError` | Не хватает обязательного файла |
| `ImportCancelled` | Импорт отменён |
| `PluginError` | Прочая ошибка плагина, установки или протокола |

Ошибки, отмена и тайм-аут не заменяют ранее сохранённый результат импорта.

## Установка и выполнение

`PluginInstaller` создаёт отдельный `venv` для нового кандидата. pip устанавливает
wheel без обращения к сети; зависимости должны быть wheel-файлами рядом с пакетом.
SDK и worker копируются из приложения в `runtime`. Отдельный дистрибутив
`partsdb-plugin-api` через pip в этой реализации не требуется и не устанавливается.
Дополнительная entry point-группа в метаданных wheel не используется:
точка входа берётся из манифеста.

Реестр `plugins.json` находится в каталоге установленных плагинов, а поколения
окружений — в его `.installs/`. Из исходников используется Python приложения;
в сборке PyInstaller — установленный `python3` либо `plugins.python` из конфигурации.
Минимальная версия интерпретатора плагина — 3.9. Подробная раскладка и конфигурация
приведены в [инструкции runtime](plugin-runtime.md).

`PluginRunner` запускает worker в отдельном процессе, обменивается JSON-строками,
обрабатывает журнал и прогресс. Тайм-аут по умолчанию — 120 секунд; предел сообщения —
16 MiB. Обычный stdout плагина перенаправляется в stderr. Фоновая задача Qt не
использует соединение SQLite; сохранение выполняется в GUI-потоке после предпросмотра.
Отдельный процесс защищает приложение от сбоя импортёра, но не является песочницей.

## Обновление и ответственность приложения

Установщик проверяет новое окружение до переключения действующей установки.
При обновлении и замене должны совпадать функциональный тип и внешняя система.
Ошибка оставляет прежний плагин доступным. Приложение работает только с текущей
открытой базой и не обходит другие пользовательские базы.

Импортёр обязан предоставлять устойчивые внешние ID физических позиций, чтобы
повторное чтение того же источника позволяло сопоставить результаты. Хранение
внутренних ID, складских соответствий и состояний обновления не является частью API.
Правила записи, удаления и соответствие полям приведены в [справочнике таблиц](database-schema.md).
Изменения формата хранения описаны в [миграциях](database-migrations.md).

## Тесты и ограничения

Текущий тестовый проект — `SMHome_UniversalRound_ESP32_C3_Mini_v4`: 49 позиций
в трёх связанных схемах. Копия файлов и эталон KiCad находятся в `tests/input`,
тесты — в `tests/kikad_plugin`. Импорт не зависит от исходного проекта пользователя.

Полный прогон и сборка плагина: `./build.sh -tp`. Очистка тестовых БД и ротация
бэкапов выполняются автоматически по результату тестов; правила описаны
в [инструкции проверки](plugin-runtime.md#проверка-и-очистка-тестовых-бд).

Автоматический подбор аналогов, сетевой каталог плагинов, установка из PyPI,
офлайн-ZIP и декларативные пользовательские настройки остаются расширениями.


## Правила организации кода

Запросы приложения централизованы в `ElData/ElDBScheme.py`: список проектов,
типы иконок, метаданные плагинов, запись позиций и сопоставлений. SQLite-драйвер,
транзакции, PRAGMA, `sqlite_master` и `sqlite_sequence` находятся в
`ElData/ElDBConnect.py`. Вне этой пары SQL не исполняется; исключение — тесты.
Корневой `connector.py` удалён. [Методы SQLite-драйвера](sqlite-driver.md). Интерфейс передаёт
сервисам `DBScheme`, а не сырое соединение. Поддержка старых вызовов с соединением
сохраняется через `DBScheme.using()`; операция не открывает новую базу.

Остальные правила записаны в [AGENTS.md](../AGENTS.md): файлы данных
`ElDBDataProj.py`, `ElDBDataParts.py`, `ElDBDataPlagins.py`, общий файл констант
`ElConstants.py`, описания классов и методов. Они применяются к новым частям кода;
перенос существующих классов и констант выполняется по отдельной команде.
Перед созданием другого файла данных его имя согласовывается с пользователем.
Классы внешних API исключены из правила размещения DB-моделей. Классы и структуры
иконок по правилам 2 и 3 пока остаются на прежних местах.
